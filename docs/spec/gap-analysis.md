# 요구사항 대비 갭 분석과 보완 백로그

요구사항 정의 v1.0(`docs/spec/requirements.md`)과 현재 코드·문서를 대조한 결과. 요구사항 상태의 정본은 `README.md` 체크리스트고, 이 문서는 **"무엇이 비어 있고 어떤 순서로 채울 것인가"** 만 소유한다. 항목을 끝내면 체크하고 `README.md` 상태를 갱신한 뒤 `last_verified`를 맞춘다. 완료 항목도 지우지 않고 보존한다 — 무엇이 비어 있었고 어떤 순서와 시행착오로 채웠는지의 기록이 이 문서의 두 번째 소임이다 (사용자 결정, 2026-09-05).

점검 방법: 앱 소스 15개와 `main...HEAD` 변경 18개 파일을 읽고 요구사항 정의(필수·선택·문서 구성·필수 조건)와 대조. 코드에 있으면 "구현", 실기기 증거가 없으면 "미검증"으로 판정 (`AGENTS.md` 절대 금지 1항).

## 1. 판정 요약

필수 기능(R1~R4), 실기기 증거, 성능 수치, LLM 리포트 필수 항목이 준비돼 있다. 남은 제출 준비는 별도 데모 영상 촬영과 전달 링크 확정이다.

## 4. 선택 요구사항은 아니지만 품질 약점

- **바닥·천장 구분의 시작 높이 가정.** `OccupancyGrid.wallBand`가 스캔 시작 시 기기 높이(바닥 위 1.2~1.5m)에 의존한다. `ARPlaneAnchor` 수평면의 최저 y를 밴드 기준으로 쓰면 가정이 사라지고, 바닥·천장 구분이라는 "정답 없는 문제"에 대한 판단 근거가 된다. 실기기에서 앉아서 시작해 보고 실제로 깨지면 우선순위를 올린다 (`DESIGN.md` 6절 되돌리기 1순위).
- **커버리지 표기.** 상태 표시의 `cells` 수에 셀 면적(0.0025m²)을 곱해 m²로 보이면 R1-3 피드백이 한 줄 변경으로 읽기 쉬워진다.
- **성능 측정 경계 (09-06 3차 녹화).** 내부 p50·p95·메모리는 Debug 진단 빌드와 명령줄 조건으로 만든 Release 계측 빌드 양쪽에서 3분 이상 측정했다. 진단 패널의 좌표·기록 탭·격자만 보기·초기화 세대는 같은 날 Development 진단 녹화에서 확인했다 (`README.md` 매트릭스). 남은 공백: 패널 켬/끔 부하 차이와 발열 영향을 분리하지 않았다 (두 편 연속 촬영으로 `높음` 상태, `DESIGN.md` 10절).
